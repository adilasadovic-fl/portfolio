Case Study

Executable Collaboration

A code-based framework for design × engineering.

Company
Miro
Role
Framework Designer
Scope

Status
Active practice · piloting with additional teams

The problem

Design and engineering were working on the same product, but not in the same system. Design lived in mockups. Feasibility discussions happened somewhere else. Changes were announced in Slack. Documentation decayed. Engineers regularly had to determine which artifact represented the latest intent.

I started questioning whether this was really a communication problem. What if the underlying problem was the artifact itself?

The problem had been there for years

This wasn't an AI problem. An internal engineering study in 2022 surfaced three recurring frustrations with design collaboration: feasibility discussions happened too late, mockups became outdated, and documentation was incomplete.

Three years later, a workshop across design and engineering produced almost the same signal. The strongest pain point was unclear source of truth, followed by low visibility into design changes, design-system misalignment, communication overhead and missing changelogs.

Across both research moments, five problems kept resurfacing: source of truth — where does the latest product intent actually live; feasibility — when does engineering have enough access to challenge technical assumptions; documentation — why are teams manually documenting information already implicit in the work; design-system drift — how do prototypes stay aligned with the components engineers actually ship; and visibility — how does engineering know what changed without designers repeatedly broadcasting it.

Different teams. Different years. Different tools. Same structural problems.

Static design artifacts make collaboration problems inevitable because the artifact cannot participate in the engineering system around it.

The system

The framework is built around one shift: from a representation of the product to a running version of the product. A designer uses an AI-assisted development environment to build the interaction directly with production design-system components. That prototype enters version control. From there it behaves much more like engineering work.

Five layers make the system work

The framework separates the workflow into five concerns.

01 — Creation · Build the interaction instead of only describing it

Designers work directly in code with AI assistance. The goal isn't to turn designers into frontend engineers — it is to make the interaction itself available for inspection much earlier. Complex states, responsive behavior and edge cases can be experienced rather than inferred from static frames.

02 — Source of truth · Version the work and its reasoning

Running prototypes live in a shared Git repository. Changes have history. Experiments can happen safely on branches. Meaningful design decisions are documented alongside the work through Design Decision Records, adapting the engineering pattern of Architecture Decision Records for design. The repository therefore captures both what changed and why it changed.

03 — Render & review · Review the same thing that changed

Every pull request creates a live preview. Designers and engineers review the running interaction through the same change request rather than splitting feedback across a design file, a prototype and Slack. The important shift is not the preview itself — it is that feedback becomes anchored to a version of the work. When the design changes, its review history doesn't disappear.

04 — Communication · Generate updates from the work instead of rewriting the work

Once changes are structured in version control, the system can understand what changed. AI-assisted workflows use that history to draft updates for communication and documentation tools. The designer still decides what matters and approves everything before it is published. The principle is: automate transcription, not judgment.

05 — Design system · Use production components, not visual approximations of them

A coded prototype is still unreliable if its components merely imitate the production design system. The framework consumes the actual design-system packages engineers use — removing an entire category of drift. If a production component changes, the prototype changes with it. If a company's design system cannot be consumed this way, that limitation becomes visible immediately rather than being hidden behind visually accurate mockups.

One review loop instead of parallel conversations

One of the biggest weaknesses in the first version of the system was review. The source of truth lived in Git, while prototype comments could live somewhere else — that simply moved the original source-of-truth problem from design into feedback. So I changed the model: a pull request now becomes the collaboration object.

↓

↓

↓

The preview is where people experience the work. The pull request is where the decision happens. The repository remains the record.

Design Decision Records

There was another problem static design tools handle poorly: why did we choose this? Engineering already has a useful pattern for this — Architecture Decision Records. I adapted that idea into Design Decision Records. A DDR captures the decision being made, the context behind it, alternatives considered, trade-offs, the chosen direction and consequences.

It also answers a surprisingly important question: what happens to the prototype? Executable doesn't automatically mean production-ready. For each project, the team explicitly names whether the prototype is production code, a reference implementation, a specification, or temporary exploration.

The default model in this framework is spec-first. The running prototype becomes a reference implementation engineering can inspect and compare against rather than code that is automatically assumed to ship. That distinction prevents "designing in code" from becoming an expensive way of producing disposable mockups.

Closing the engineering feedback loop

The original collaboration problem wasn't only that engineers couldn't see changes. Research showed that feasibility discussions happened too late — visibility alone isn't enough. Engineering needs a path back into design. Technical questions, implementation constraints and feasibility concerns flow back through the same pull request and repository. Design doesn't send a finished answer downstream; the artifact stays open to technical challenge while the solution is still changing.

This is one of the main reasons I think of the framework as collaboration, rather than a better handoff mechanism.

Communication becomes an output of the system

Two lightweight workflows handle most change communication.

Notify — the system reads recent changes and drafts an update appropriate to their significance. Small paper cuts may not need an announcement. Meaningful changes can generate proposed messages and related ticket updates. The designer previews, edits and confirms before anything goes out.

Digest — at a chosen cadence, repository history becomes the starting point for a broader project update: meaningful changes, versions, related work and current previews. Again, AI drafts. A human publishes. An automated safety net catches important changes that were merged without being communicated.

The intent isn't more automation. It's less duplicated work.

From my workflow to a team workflow

The framework began in the Content Security design × engineering team, where it is now used as an active working model. That proved it could work in one environment. It did not prove it could scale.

The initial conditions were unusually favourable: I was already comfortable working with Git and had a close working relationship with engineering. A Staff-level system should not depend on the person who invented it. So instead of treating the first implementation as proof, I designed the next phase as a pilot. Additional teams are now adopting the workflow under deliberately less ideal conditions, including designers with less Git experience and different design–engineering relationships.

The question isn't "can other teams follow my process?" It's: which parts of the system survive when I'm no longer the person operating it?

What we're testing

The pilot focuses on three measures, baselined before adoption and measured again during the pilot: design iteration cycle time — how long it takes to move from an idea to something design and engineering have actually reviewed; engineering visibility — do engineers understand what changed in design and why without reconstructing that information from multiple tools; and documentation overhead — how much time is spent manually maintaining updates, specifications and changelogs.

The point isn't to validate the framework. The numbers are allowed to prove it wrong.

A maturity model

Adoption moves through four stages, incrementally rather than as an all-or-nothing transformation.

01
Static
Design lives primarily in a design tool. The latest artifact is the truth.
02
Linked
Designs are connected to tickets and documentation. Truth remains distributed.
03
Executable
Running prototypes live in version control with preview-per-change and shared review. The repository becomes the source of truth.
04
Integrated
Creation, design system, review, decision history and communication operate as one connected workflow.

What I don't think the framework solves yet

Git fluency is still a dependency. AI makes code creation far more accessible, but designers still need a working mental model of commits, branches and pull requests. How much fluency is enough remains an open question.

Discipline is easier to design than maintain. Decision records and clean version histories are easy to value when a team has time. Deadline pressure is the real test. Some behavior can be enforced through tooling. Good judgment cannot.

Tooling creates dependencies. The framework is conceptually tool-agnostic. Any real implementation isn't. Preview environments, AI coding tools and integrations all create dependencies that need to be understood rather than ignored.

Executable doesn't mean production. The relationship between prototype and production code must remain explicit. Without that agreement, executable design can simply create a more technically sophisticated version of the old handoff problem.

Reflection

The framework is now part of the working practice of the team where it was created and is being tested with additional teams. For me, the project has moved beyond a question of tooling. It started with: how can designers work more effectively with engineers? The more useful question became: what should the shared artifact between design and engineering actually be?

My answer is still being tested. But it is no longer a static picture.
