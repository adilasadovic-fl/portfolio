The problem

Miro is designed around openness. Put something on a canvas. Invite people in. Share ideas quickly. Let the board evolve.

Enterprise security introduces the opposite requirement. Some content should make a board less open.

Security Mode is the system I designed around that contradiction: when a board is classified as sensitive, its security posture changes. Access can narrow, sharing can be constrained, detected content can be reviewed and resolved, and changing the board back requires a governed path.

Security should change the state of the board, not turn the product into a wall of restrictions.

The collaboration continues. The rules around it change.

A canvas creates a different security problem

Sensitive-content protection is relatively easy to imagine in a structured document. A Miro board is different. Over its lifetime it can accumulate sticky notes, screenshots, tables, diagrams, uploaded files, embedded content and free-form text from many contributors. Sensitive information can appear almost anywhere.

At the same time, almost every interaction in the product is optimized to reduce friction around collaboration. That creates a fundamental tension. Move too far toward control and legitimate work becomes painful. Move too far toward collaboration and sensitive information remains exposed. Most of the design work happened somewhere on that line.

Collaboration ←──────→ Control

The system

The experience can be understood as one lifecycle. Each stage changes what the user, the administrator or the system is allowed to do. That meant the design problem couldn't be solved screen by screen — the interaction model, permissions model and system behavior had to agree.

01 — Detect

Sensitive content can be surfaced through different forms of detection. Some are relatively deterministic, such as structured information types or configured keywords. Others rely on machine-learning-based sensitivity signals and cannot always provide a precise human-readable explanation for why something matched.

The first challenge was therefore not simply displaying a result. It was designing one review model across detection technologies with very different levels of explainability. The experience asks the same questions regardless of detection type: what was found, where is it, what does the system know about it, what can I do next. The quality of the explanation may vary. The mental model does not.

02 — Classify

Detection alone doesn't define the board's security state. A board can become classified through automated rules or through people who have the authority to classify it. Classification introduced an authority problem: who is allowed to decide that a board is sensitive, and who is allowed to decide that it isn't anymore. Those two permissions cannot be treated as equivalent — classifying a board generally increases protection; reclassifying it can remove protection. The design model had to distinguish between the two and make authority part of the product behavior rather than burying it in an admin setting.

Key decisions

Decision 01

Make protection a board state

Constraint
Every security event — a restricted share, a sensitive-content match, a classification change — could be handled as a separate, unrelated interruption.
Competing options
Treat each security event independently with its own warning or banner, versus giving the board one persistent, coherent state.
Reasoning
Technically, isolated events could all work. Conceptually, they leave users without a stable answer to a basic question: what kind of board am I working in?
Chosen model
Classification moves the board into a persistent protected state. Security Mode becomes part of the board's identity — access expectations change consistently, sharing follows policy, and review and remediation belong to the same security model.
Consequence
The user isn't encountering unrelated security interruptions. They're working inside a board whose posture has changed.
Decision 02

Protect without removing the product

Constraint
A straightforward security solution would be to lock down everything — but that would undermine the reason people use Miro.
Competing options
Broad restriction across the whole board versus targeted restriction of only the behaviors that increase exposure.
Reasoning
The starting question isn't "what should we disable?" — it's "which behavior actually increases exposure?" That reframing produces much more targeted intervention.
Chosen model
Restrict what the risk requires. Preserve everything else. The protected board should still feel like a board — people can still think, work and collaborate inside it unless a particular action introduces risk.
Consequence
Protection reads as a change in posture, not a removal of the product.
Decision 03

Bring remediation to the content

Constraint
Security systems traditionally surface problems to administrators — but an administrator often isn't the person who understands why a particular piece of content exists or what should happen to it.
Competing options
Centralize remediation in an admin console versus connect admin governance with in-context remediation where the content actually lives.
Reasoning
The person closest to the content is usually the board owner or contributor, not the admin. Forcing them to translate an abstract security alert back into a visual workspace adds a costly extra step.
Chosen model
On the board, people can inspect sensitive-content findings where those findings actually live — combining a list of detected matches, the spatial canvas context, and detail for the selected finding.
Consequence
The content and the security decision remain connected.
Decision 04

Make false positives a primary flow

Constraint
False positives aren't an edge case in automated detection — they're part of the system, and their cost is different from a false negative's cost. A false positive can interrupt legitimate work and erode trust in future detections.
Competing options
Design only for the happy path (accept, resolved) versus treat review, dismissal and reclassification as first-class paths.
Reasoning
Designing only for the happy path would create a system that slowly teaches people to ignore it.
Chosen model
Where the underlying detection technology can explain a result, the interface exposes that evidence. Where it cannot, the product compensates with clearer review states, careful language and an obvious human decision path.
Consequence
The goal isn't to make automation appear more certain than it is — it's to make the limits of the automation manageable.
Decision 05

Treat configuration as part of the threat model

Constraint
Administrators need flexibility, but some configuration changes can weaken protection — the configuration surface itself becomes part of the security problem.
Competing options
Make every setting configurable versus introduce guardrails wherever a setting could undermine the security model.
Reasoning
This changed the design question from "which settings do admins want?" to "which degrees of freedom are safe to expose?" — a much more consequential product decision.
Chosen model
Security Mode's policy model works across reclassification strictness, trigger conditions, false-positive handling and classification permissions, with guardrails built into each.
Consequence
Configuration flexibility is bounded by what the security model can safely allow.

How it works

Security Mode has two main operating surfaces that rely on the same underlying state and permission model.

On the boardWhere collaboration happens — protected status, review, remediation
↔
In administrationWhere policy is defined — classification, permissions, visibility

On the board, people need to understand that the board is protected, what content triggered review, where that content exists, what action they can take and what effect that action will have. Security needs to remain legible without dominating the workspace.

In administration, administrators need to control classification behavior, permissions, protection rules, remediation policy and visibility across protected content. The board is where the problem is resolved. The admin surface is where the rules are governed.

The hardest design work happened below the interface

A significant part of Security Mode wasn't visual design. It was defining behavior. Where does the authoritative configuration live? What happens when a board changes classification while people are already working in it? Which actions remain available in each state? How do permissions behave during reclassification? How do multiple detection mechanisms resolve into one board-level state? What happens when policy and user intent disagree?

These questions were worked through directly with product and engineering. Design owned the flow and access models used to reason about the system, not only the screens produced after those decisions. The interface became the visible consequence of a much deeper behavioral model.

Outcome / status

The core Security Mode experience is available to enterprise customers. Review and remediation have expanded the system from simply protecting sensitive boards toward helping people understand and resolve the content that caused protection in the first place. Configuration and administrative visibility continue to build around the same underlying model.

Reflection

Security products are often described as a balance between usability and control. I think that's slightly misleading. The goal isn't to compromise until both sides are equally unhappy. The better question is: where is friction actually justified by risk?

Some actions should remain effortless. Some should require explanation. Some should require authority. And some should simply not be possible. Security Mode taught me to treat those as product-state decisions, not UI states. The interface only becomes clear once the system has decided what people are allowed to do, what the machine knows, and where human judgment must take over.
