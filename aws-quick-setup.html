Case Study

AWS Quick Setup

Hiding cloud complexity behind user intent.

Company
AWS · Management Tools
Role
Product Designer
Scope
Multi-account, multi-Region configuration
Status
Shipped · platform adopted by other AWS teams

The problem

AWS gives operators enormous control. That control also creates complexity. Configuring an operational capability can involve understanding multiple services, permissions, accounts, Regions and infrastructure dependencies before the user can accomplish the thing they actually came to do.

Within AWS Management Tools, we were working on a broader shift away from experiences that mirrored AWS's internal service structure and toward workflows organised around customer intent. Quick Setup was one expression of that strategy.

Let the customer define the outcome. Let the system handle the orchestration.

AWS already had the underlying services customers needed. The problem was assembling them. A DevOps engineer or IT administrator might need to configure infrastructure across services, accounts, Regions, permissions, resources and organizational units. Each individual system could be technically correct while the end-to-end task remained difficult. The customer experienced the seams between services.

That created a different kind of design question: how much of the underlying system does someone need to understand before they can safely configure it? Too much abstraction and experienced operators lose confidence and control. Too little abstraction and everyone is forced to reconstruct AWS's internal architecture just to complete a common task. Quick Setup had to sit between those extremes.

The system

Traditional infrastructure configuration often begins with the system: which service, which resource, which policy, which Region, which account. We reversed the direction — start with what you're trying to set up, then progressively ask only for the decisions the customer actually needs to make.

Underneath that simple flow could sit multiple AWS capabilities and infrastructure operations. The interface didn't remove that complexity — it moved it to the layer where it belonged.

Key decisions

Decision 01

Start with a library of outcomes

Constraint
Customers needed a way in that didn't require first identifying every AWS service involved.
Competing options
Expose the underlying services and let customers compose their own configuration from scratch, versus offer a library of recommended configurations built around common operational needs.
Reasoning
Composing from scratch preserved maximum flexibility, but also preserved most of the original complexity.
Chosen model
Customers select the capability they want rather than first identifying every service needed to create it — changing the entry point from "configure these AWS services" to "set up this operational capability."
Consequence
The distinction looks small in the interface. Architecturally, it changes who carries the cognitive load.
Decision 02

Separate "what" from "where"

Constraint
A configuration might need to apply to one resource, one account, selected accounts, selected Regions, or an entire organisation.
Competing options
Mix capability configuration and deployment scope into a single decision, versus treat them as two separate decisions.
Reasoning
Infrastructure tooling often mixes "what should happen" with "where should it happen" — that conflation gets harder to reason about as scale increases.
Chosen model
AWS Quick Setup supports configuration across individual accounts as well as multiple accounts and Regions through AWS Organizations, with capability and scope handled as distinct steps.
Consequence
Customers get a more stable mental model even as the scale of the operation changes dramatically — the same interaction can represent a small configuration or an organization-wide one.
Decision 03

Recommended defaults first, control second

Constraint
Infrastructure interfaces often treat flexibility as the same thing as exposing options — but every additional field can represent a permission, infrastructure or operational decision with real consequences.
Competing options
Expose full configurability up front, versus lead with recommended defaults and allow deeper customization when needed.
Reasoning
Most customers should not need to make every possible decision.
Chosen model
Quick Setup used recommended defaults based on AWS guidance so customers could move quickly through common configurations, while still allowing deeper customization when the defaults didn't fit — recommended path first, advanced control when needed.
Consequence
Faster time-to-configuration for the common case, without removing control for the expert case.
Decision 04

Show the consequence before deployment

Constraint
Abstraction creates a trust problem — if the system is doing work on the customer's behalf, the customer needs to understand what will happen before committing to it.
Competing options
Deploy directly from the recommended configuration, versus preview the actions and scope before deployment.
Reasoning
The system could hide implementation complexity without becoming opaque — the customer didn't need every low-level step in the primary workflow, but still needed enough visibility to make an informed infrastructure decision.
Chosen model
Selecting a configuration led to a preview of the actions and scope before deployment — customers see what would be created and where it would run before applying a configuration.
Consequence
Confidence in an automated system without requiring the customer to inspect every underlying step.

Designing for one resource and an entire organisation

Multi-account UX changes the nature of apparently simple controls. A selector is no longer just a selector when the choice may affect infrastructure across dozens or hundreds of environments. The design needed to make scope continuously legible: what am I changing, where will this change apply, how broad is the blast radius, can I verify the target before I deploy.

This is one of the areas where my broader Systems Manager work was particularly relevant. I also worked on cross-account experiences that allowed customers to view and act on applications across AWS Organizations, alongside operational workflows spanning observability, cost, compliance and security. Those projects shared the same underlying challenge: enterprise infrastructure becomes much harder to understand when the unit of interaction grows from one resource to an organization.

A platform, not just a wizard

The configuration library wasn't intended to be a fixed collection owned by one team. The system was designed so other AWS teams could contribute configurations for their own capabilities while relying on the same setup model — a platform that allowed other AWS teams to publish their own configurations and workflows.

That changed the design problem. We weren't only designing a setup flow — we were defining a repeatable grammar for setup.

A new configuration could vary in parameters and underlying services while retaining the same interaction model. That consistency mattered for customers, and created leverage internally — new capabilities didn't need to invent a new setup experience from scratch.

Complexity still exists under the interface

One of the lessons from the project was that good enterprise UX doesn't necessarily make the underlying system simpler. Sometimes the underlying system should remain complex. Cloud infrastructure has real accounts, permissions, Regions, dependencies and failure conditions. Pretending otherwise would be dangerous.

Expose complexity when the customer needs to reason about it, and absorb it when they don't.

Quick Setup made the simple path genuinely simple without removing the deeper model required by expert users.

Outcome / status

Quick Setup sat inside a much larger Management Tools transformation, so I would not attribute the program's business outcomes to one feature or one designer. The publicly documented program reports improvements including 64% cross-feature adoption, a 20% reduction in time to first cross-feature, and 50% month-over-month growth in cross-account deployment. I treat those as evidence of the broader direction rather than a causal claim about Quick Setup alone.

The more important product outcome for this case study is structural: customers could increasingly operate AWS around tasks and desired outcomes rather than manually navigating the service architecture underneath them.

Reflection

Quick Setup changed how I think about technical product design. Complexity isn't inherently bad. Unnecessary exposure to complexity is.

In infrastructure products, the designer's job isn't to make the system look simple. It's to understand the system deeply enough to know what the customer must understand, what the customer may want to understand, and what the product should handle for them. That distinction has stayed central to how I design enterprise systems ever since.
