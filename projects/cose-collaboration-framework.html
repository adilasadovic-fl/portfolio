Beyond Handoff

Designing a code-based collaboration framework so the prototype design and engineering review is the same thing production ships from — not a static stand-in for it.

Team
Miro — COSE (Content Security)
Role
Design × Systems
Timeline
2025 – ongoing (2026)
Status
Active pilot
Overview

Design–engineering collaboration at Miro's COSE team ran through disconnected tools — Figma files, Replit demos, scattered Slack updates — where the artifact under review was never the same thing engineering actually built.

We replaced that with a shared, code-based system: designers work directly in code with AI assistance, push to a GitHub monorepo as the single source of truth, render live prototypes for review, and communicate through AI-drafted, human-approved updates. The design artifact becomes executable — a running prototype in version control — rather than a static mockup that goes stale the moment engineering starts building.

AI is the enabler here, not the cause. The problems this framework solves — unclear ownership of the source of truth, feasibility gaps, undocumented decisions — were confirmed by internal research back in 2022, long before AI tooling entered the picture.

01 — The Problem

The same five problems, four years apart

A 2025 COSE workshop and a 2022 internal research study — run independently, years apart, from opposite sides of the design/engineering divide — surfaced the same failure modes. That recurrence is the strongest evidence the problem isn't a tooling gap AI can paper over; it's structural.

9/44
workshop votes named "unclear source of truth" the top pain point
15
engineers surveyed in 2022 (12 FE, 2 TL, 1 BE), plus 3 in-depth interviews

Feasibility discussions, outdated mockups, and lack of documentation ranked as the top three engineering pain points in 2022 — and reappeared, nearly unchanged, in the 2025 workshop.

The five recurring problems: unclear source of truth, feasibility gaps between design intent and engineering constraints, documentation overhead, design-system misalignment, and low visibility into design changes as they happen.

02 — The System

A four-layer model, tool-agnostic by design

The framework is deliberately described as four concerns, not four products — Miro's implementation happens to use Cursor, GitHub, Vibelab and Slack, but the model holds if any layer is swapped out. A prototype only counts as "beyond handoff" if all four layers connect: skip one, and you're back to a relabeled handoff.

Fig. 1 — The four-layer model as implemented at Miro, with the fifth "design system as code" layer identified in review as a required addition, not yet built.

03 — Deep Dive

Layer 2 — the monorepo

content-security-designs is the single source of truth: main is production state, feature branches are experiments, and Vibelab deploys straight from the repo. Two conventions do the heavy lifting —

  • Semver per package — major for new components/features, minor for smaller changes, patch for paper cuts.
  • Conventional commits driving auto-changelog generation and version bumps.
  • Design Decision Records in docs/ — the design analog of engineering ADRs, so a decision has a permanent, linkable home instead of living in a Slack thread.

04 — Deep Dive

Layer 4 — communication without the manual status update

Two Cursor slash commands carry the load, with a GitHub Actions safety net behind them so nothing silently drops.

Fig. 3 — Notification is human-in-the-loop by default; the Actions workflow only catches unnotified major bumps, which is itself a known gap (see reflection, below).

  • Config-driven: .cose/config.json per project sets default Slack channels, Jira project key, Confluence parent page, and notification defaults per version type.
  • Nothing auto-publishes. The designer always previews and confirms before a message or ticket goes out — the AI drafts, it doesn't decide.
05 — Validation

Why this isn't just an AI-tooling trend

The 2022 study and the 2025 workshop surfaced near-identical pain points from different sources, three years apart, before generative AI was part of the design workflow at all. That's the core argument for the framework: AI makes the system practical to build now, but it isn't solving a problem AI created.

  • 2022 leadership offsite: trust issues between design and engineering, need for earlier engineering involvement, prototyping named as an urgent need.
  • 2025 workshop top solution areas: documentation, design system, ready mockups, communication — the direct inverse of the pain points.
06 — Reflection

Where this is still weak

A structured review in July 2026 pushed back on the framework rather than defending it. Ranked by how much each one threatens the core thesis — that the prototype is genuinely the source of truth:

01

Review lives apart from the source of truth

Comments sit in Vibelab, anchored to elements; truth sits in git. Feedback isn't versioned or tied to a commit, and evaporates on the next iteration — this relocates the #1 pain point (unclear source of truth) onto feedback itself. The biggest structural crack in the system.

02

"Beyond handoff" may just be handoff, relabeled

The prototype lives in a designs repo; production code lives elsewhere. The boundary moved, it didn't disappear. The open question is whether prototype code is reused, referenced as spec, or thrown away — if thrown away, this is an expensive Figma.

03

Feasibility flows one direction

There's no explicit channel for engineering to push feasibility concerns back into the prototype — despite feasibility being the #1 engineering pain point in 2022.

04

Design-system drift may widen, not close

Designers pull Figma components by reference rather than consuming MDS as code, so the rendered prototype can silently diverge from the production component it's supposed to represent.

05

n=1 proof behind a Miro-wide ask

The proof point is one git-fluent designer with a tight engineering relationship. Median designer git fluency and DDR discipline are large, untested adoption assumptions.

Fixes in motion
  1. Collapse review into the PRPR → auto Vibelab preview URL → comments resolve in the GitHub PR thread → merge. Fixes the source-of-truth split and unifies design + engineering review into one ritual.
  2. Import MDS as code, not Figma referencesMakes drift impossible by construction. If MDS isn't consumable as code, that's the real blocker to surface — not a UI polish issue.
  3. Name the prototype's fate explicitlySpec, reused, or discarded — decided per project, with the eng→design feedback loop designed around that answer.
  4. Notify on minor too, batched into the digestSeparates "silent" from "noisy" instead of choosing one.

If only two things get fixed next: collapsing review into the PR, and answering what happens to the prototype code.
